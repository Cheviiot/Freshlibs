# Freshlibs

Репозиторий [Stapler](https://stplr.dev) со **свежими системными библиотеками**
для ALT Linux 11.2 (платформа p11).

ALT p11 — стабильная платформа с замороженными версиями. Это хорошо для системы
и плохо для разработки: часть библиотек в ней отстаёт от upstream на годы или
собрана без нужных плагинов. Freshlibs собирает такие библиотеки из upstream-исходников
под правилами ALT и **вытесняет системные одноимённые пакеты**, сохраняя
совместимость по ABI (soname и set-version-зависимости остаются те же), так что
уже установленные пакеты p11 продолжают работать.

Это репозиторий низкоуровневых библиотек, а не приложений. Прикладные программы
живут отдельно, в [Nivora](https://github.com/Cheviiot/Nivora).

> [!WARNING]
> Пакеты из Freshlibs заменяют пакеты базовой системы: при установке
> соответствующие системные пакеты (`libdecor-0`, `libdecor-devel`, …) удаляются
> через `Obsoletes`/`Conflicts`. Это осознанный выбор, а не побочный эффект,
> но откат нужно делать вручную — см. [Удаление и откат](#удаление-и-откат).

## Состав

| Пакет | Freshlibs | В p11 | Что даёт |
| --- | --- | --- | --- |
| [`libdecor-0`](libdecor-0/) | `1:0.2.5` | `0.1.1-alt1` | GTK-плагин декораций (в p11 только cairo), 2.5 года upstream-исправлений; заменяет `libdecor-0` и `libdecor-devel` |

Каждый пакет содержит и runtime, и devel-часть (заголовки, `.pc`, symlink `.so`):
системный devel-пакет владеет теми же путями, поэтому его приходится заменять,
а не держать рядом.

## Требования

- ALT Linux 11.2 / p11, `x86_64` или `aarch64`
- Stapler `v0.1.1` или новее (`stplr version`)

## Подключение

```bash
stplr repo add freshlibs https://github.com/Cheviiot/Freshlibs.git
stplr refresh
```

Имя репозитория (`freshlibs`) попадает в имя собираемых пакетов как суффикс:
`libdecor-0` превращается в `libdecor-0+stplr-freshlibs`. Это нормально —
именно поэтому пакеты объявляют `provides`/`conflicts`/`replaces` на системные
имена, а не полагаются на совпадение имени.

## Установка

```bash
stplr install libdecor-0
```

Stapler соберёт пакет локально (для этого он доустановит сборочные зависимости
из репозиториев ALT), затем отдаст его `apt-get`, который удалит системные
`libdecor-0` и `libdecor-devel` и поставит новый пакет.

## Проверка

```bash
pkg-config --modversion libdecor-0        # 0.2.5
ls /usr/lib64/libdecor/plugins-1/         # libdecor-cairo.so + libdecor-gtk.so
rpm -q libdecor-0+stplr-freshlibs
```

Что должно получиться:

```
0.2.5
libdecor-cairo.so  libdecor-gtk.so
libdecor-0+stplr-freshlibs-0.2.5-alt1.x86_64
```

Наличие `libdecor-gtk.so` — главное отличие от p11: libdecor выбирает плагин по
приоритету и предпочитает GTK-плагин, поэтому Wayland-приложения без своих
декораций (в том числе на SDL3) получают заголовок и рамку в стиле GNOME вместо
минималистичного cairo-фолбэка. Перезапустите приложения после установки —
плагин загружается при инициализации libdecor.

Полезные переменные окружения для диагностики:

```bash
LIBDECOR_PLUGIN_DIR=/usr/lib64/libdecor/plugins-1 your-app   # явный каталог плагинов
```

## Обновление

```bash
stplr refresh
stplr upgrade
```

`stplr refresh` подтягивает рецепты из этого репозитория, `stplr upgrade`
пересобирает и переустанавливает то, что обновилось.

Штатный `apt-get update && apt-get dist-upgrade` откатить библиотеку назад не
может: установленный пакет называется `libdecor-0+stplr-freshlibs`, конфликтует
с системным `libdecor-0` и объявляет его устаревшим, поэтому apt не станет
возвращать `0.1.1`. `epoch=1` в рецепте — вторая линия обороны: любая будущая
версия из Freshlibs всегда сортируется выше версии без epoch.

## Удаление и откат

Правильный способ вернуться на системную версию — **одна команда**, а не
удаление:

```bash
apt-get install libdecor-0 libdecor-devel
```

apt делает обмен в одной транзакции: снимает пакет Freshlibs и ставит
системные `0.1.1`, ничего больше не трогая.

Голое удаление разрушительно, и это не предположение, а план самого apt:

```
$ apt-get -s remove libdecor-0+stplr-freshlibs
Следующие пакеты будут УДАЛЕНЫ:
  gnome-session-wayland  libdecor-0+stplr-freshlibs  xorg-xwayland
  i586-steam.32bit       mesa-gears
```

Пакет от этого защищён: он сам восстанавливает состояние.

`%post` при установке и при каждом обновлении записывает в
`/var/lib/freshlibs/libdecor-restore.list` замыкание установленных пакетов,
которым нужен libdecor. Список снимается именно здесь, а не при удалении:
`apt-get remove` сносит зависимые пакеты **раньше**, чем доходит до наших
скриптлетов, и `%preun` увидел бы уже пустую базу (проверено в контейнере —
rpm снял `mesa-gears` и `xorg-xwayland` первыми). `%preun` дополняет список
свежим обходом, на случай пакетов, поставленных после последнего обновления.

`%postun` передаёт список одноразовой службе systemd: вызвать apt из
скриптлета нельзя, он исполняется внутри транзакции rpm и держит блокировку
базы. Через десять секунд после операции служба возвращает системный libdecor
и всё, что apt унёс вместе с ним:

```bash
journalctl -u freshlibs-restore-libdecor    # ход восстановления
```

Восстановление устроено осторожно: оно не сработает при обновлении пакета,
молчит при обмене (тогда системный libdecor уже стоит), ставит только реально
отсутствующие пакеты и **отказывается действовать**, если план apt содержит
хоть одно удаление — в этом случае в журнал попадает готовая команда для
ручного разбора. Проверка «чего не хватает» живёт в отложенном помощнике, а не
в скриптлете: внутри транзакции порядок удаления не определён, и пакет, который
apt вот-вот снимет, из скриптлета ещё выглядит установленным.

Всё это проверено целиком в контейнере ALT p11 (`distrobox`), а не только на
логике: установка, удаление с каскадом и восстановлением четырёх пакетов,
обмен, обновление и опт-аут.

Отключить автовосстановление:

```bash
touch /etc/freshlibs/no-auto-restore
```

Если репозиторий больше не нужен:

```bash
stplr repo remove freshlibs
```

## Локальная сборка

```bash
git clone https://github.com/Cheviiot/Freshlibs.git
cd Freshlibs
stplr build -s libdecor-0/Staplerfile
```

Готовый `.rpm` появится в текущем каталоге. `--clean` пересобирает с нуля,
`--no-suffix` собирает пакет без суффикса `+stplr-<репозиторий>` в имени.

> [!NOTE]
> `stplr build` доустанавливает сборочные зависимости из репозиториев ALT
> в систему, где запущен, — это не изолированная сборка.

Проверять пакеты, которые вытесняют системные, лучше в контейнере, а не на
живой машине: удаление такого пакета каскадом уносит зависимые пакеты. Годится
одноразовый Distrobox на образе p11, обязательно с systemd, иначе отложенное
восстановление не запустится:

```bash
distrobox create --name freshlibs-p11 --image registry.altlinux.org/p11/base:latest \
    --init --additional-packages "systemd rpm apt sudo" --yes
podman exec --user root freshlibs-p11 sh -c 'apt-get update && apt-get install -y ...'
```

`distrobox enter <имя> -- команда` на ALT падает (`su: invalid option -- 'm'`),
поэтому команды внутрь удобнее подавать через `podman exec`.

## Как устроены рецепты

Правила, общие для всех пакетов Freshlibs:

- **Имя пакета совпадает с именем бинарного пакета в ALT**, а не с именем
  upstream-проекта или src.rpm. Для libdecor это `libdecor-0`, а не `libdecor`:
  тогда автоматические `Provides`/`Conflicts` от Stapler попадают на нужное имя.
  Каталог пакета называется так же — документация Stapler требует точного
  совпадения имени каталога с полем `name`.
- **`epoch=1`** у всех пакетов, которые вытесняют системные.
- **`replaces`** (→ `Obsoletes`) перечисляет все системные пакеты, чьи файлы
  попадают в наш: runtime, devel и, если они есть в других дистрибутивах,
  отдельные пакеты плагинов.
- **`provides`** дублирует системные имена в версионном и безверсионном виде,
  чтобы зависимости вида `libdecor-devel >= 0.2` тоже разрешались.
- **`auto_reqprov_method='rpm'`** с `auto_req=1`/`auto_prov=1`. Это обязательно:
  только ALT-овые `/usr/lib/rpm/find-{provides,requires}` (пакет `rpm-build`)
  генерируют set-version-зависимости вида
  `libdecor-0.so.0()(64bit) = set:…`, от которых зависят пакеты p11. Универсальный
  метод `dirty` их не даёт, и такая библиотека не удовлетворит существующие
  обратные зависимости.
- **`--libdir=/usr/lib64`** на ALT: `/usr/lib64` — настоящий каталог 64-битных
  библиотек, а `pkg-config` ищет только в `/usr/lib64/pkgconfig:/usr/share/pkgconfig`.
  Рецепты определяют libdir в `prepare()` и не полагаются на `/usr/lib`.
- **`compatible_with=('altlinux')`**: имена сборочных зависимостей и layout
  каталогов здесь специфичны для ALT.
- **Скриптлеты восстанавливают состояние, а не кэши.** ALT-овый rpm сам
  обновляет `/etc/ld.so.cache` для пакетов с библиотеками (у системных
  `libcairo`, `libgtk+3`, `libwayland-client` скриптлетов нет вообще), поэтому
  `ldconfig` вызывается лишь как идемпотентная страховка. Скрипты нужны
  из-за другого: пакет подменяет библиотеку базовой системы, и её удаление
  каскадом уносит всё, что от неё зависит. Схема такая: `postinstall`
  (`%post`) записывает замыкание обратных зависимостей при установке и на
  каждом обновлении — снимать его при удалении поздно, зависимые пакеты rpm
  сносит раньше наших скриптлетов; `preremove` (`%preun`) дополняет список
  свежим обходом и копирует помощника в `/var/lib/freshlibs`, так как файлы
  пакета вот-вот удалят; `postremove` (`%postun`) передаёт список одноразовой
  службе systemd, потому что скриптлет работает внутри транзакции rpm и держит
  блокировку базы — apt из него не вызвать; отложенный
  `/usr/libexec/freshlibs/libdecor-restore` доустанавливает то, чего не
  хватает. Фильтр «чего не хватает» стоит именно в отложенном скрипте: внутри
  транзакции порядок удаления не определён, и пакет, который apt вот-вот
  снимет, ещё выглядит установленным.
- **Каждый скриптлет проверяет аргумент rpm** (`%post`: 1 — первая установка,
  2+ — обновление; `%preun`/`%postun`: 0 — настоящее удаление, 1 — обновление),
  потому что при обновлении rpm запускает `%preun`/`%postun` старой версии, и
  без проверки восстановление срабатывало бы на каждом `stplr upgrade`.
  Скриптлеты rpm исполняет через `/bin/sh`, а не по shebang, поэтому
  bash-специфичного синтаксиса в них нет.
- В `files()` не используется `files-find-binary`, если пакет не ставит
  исполняемых файлов: хелпер завершается ошибкой на пустом `/usr/bin` и роняет
  сборку.

## Добавление новой библиотеки

1. Создайте каталог, имя которого **в точности** совпадает с полем `name`
   в рецепте — это требование документации Stapler.
2. Положите в него `Staplerfile` по образцу [`libdecor-0/Staplerfile`](libdecor-0/Staplerfile).
3. Проверьте фактические имена системных пакетов и путей, а не предполагаемые:

   ```bash
   apt-cache policy <пакет>          # существует ли такое имя в p11
   rpm -ql <установленный-пакет>     # какие файлы он занимает
   rpm -q --provides <пакет>         # какие provides нужно повторить
   apt-cache rdepends <пакет>        # кто от него зависит
   ```

4. Соберите локально (`stplr build -s <каталог>/Staplerfile`) и проверьте
   метаданные готового пакета:

   ```bash
   rpm -qip <пакет>.rpm              # Epoch, Version, Group
   rpm -qp --provides <пакет>.rpm
   rpm -qp --obsoletes <пакет>.rpm
   rpm -qp --conflicts <пакет>.rpm
   rpm -qlvp <пакет>.rpm
   ```

5. Добавьте строку в таблицу [Состав](#состав).

## Известные ограничения

- Сборка в hasher/rpmbuild сторонних пакетов, которые требуют
  `libdecor-devel` по точной версии-релизу ALT (`= 0.1.1-alt1:p11+…`),
  не пройдёт: Freshlibs предоставляет `libdecor-devel = 1:0.2.5` без ALT-релиза.
  Зависимости по soname и по `>=` работают.
- 32-битные мультилиб-пакеты `i586-libdecor-0` и `i586-libdecor-devel` требуют
  64-битные по точной версии-релизу (`libdecor-0 = 0.1.1-alt1:p11+348849.100.1.1`),
  поэтому вместе с Freshlibs они не встанут. В типовой системе они не установлены;
  если 32-битный libdecor нужен, Freshlibs для libdecor не подходит.
- Автовосстановление зависит от systemd (`systemd-run`). Без systemd
  `%postun` печатает готовую команду `apt-get install ...`, но сам ничего не
  делает.
- Список для восстановления снимается при установке и при каждом обновлении
  пакета. Если после последнего обновления в систему пришёл новый потребитель
  libdecor и пакет удалили, не обновляя, этот потребитель может не попасть в
  восстановление: `%preun` добивает список свежим обходом, но rpm к тому
  моменту уже мог снять часть пакетов.
- `apt-get -s install` для этого пакета выдаёт ложное `E: Fatal, conflicts
  violated`: симуляция ALT-овского apt не умеет разыгрывать пару
  Conflicts+Obsoletes на одно имя. Реальная установка проходит штатно —
  проверено в контейнере. Не пугайтесь симуляции.
- Пакеты не подписаны: Stapler собирает их локально на машине пользователя.
- Проверено на `x86_64`. `aarch64` в рецепте объявлен (`architectures`), но
  не протестирован.
